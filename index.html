How I Map Your AI Rollout

I don't start with a shelf of kits or a platform demo. I start with your use case, then work outward to the architecture and the enablement it takes to run it.

01

Identify the Problem

What are you actually trying to solve? Before any platform or agent gets named, I run a working session to pin down the real use case — the workflow that's slow, inconsistent, or stuck waiting on one person's time. I use Agile user stories — "As a [role], I want to [do X], so that [outcome]" — to turn a vague ask into a specific, buildable problem statement. Sometimes I run this discovery step as its own agent, interviewing stakeholders directly — the use case it surfaces becomes the spec for the production agent(s) built in Step 3.

02

Map the Approach

Once the use case is clear, I map the right architecture — which platform, how many agents you actually need, and how they hand off to one another. This is also where I answer "is there a Connector for that?" — Copilot Studio ships hundreds of them, and knowing the catalog (or knowing when nothing fits) is my job, not something you have to research yourself.

03

Build & Enable

I build to the map — a single agent, a multi-agent system, or both — then enable it through change management: training, AI Champion networks, and role-based custom enablement, like my Project Manager kit example. The output fits the use case; it's never a template applied backwards.

The AI Enablement Ladder

This is the training curriculum itself, not just a platform tour — from determining a use case to advanced Copilot Studio features. For Microsoft 365 teams, each rung hands you more control over what your agent can actually do.

01

Identify the Use Case

Before any platform gets named, I train teams to determine a use case themselves.

  • Agile user stories to define the problem precisely
  • Agents built specifically to help with problem identification
  • Best for: turning "we want AI" into something buildable
02

Copilot

Everyday AI assistance built into Word, Excel, Teams, and Outlook.

  • Zero setup — on by default for every user
  • Chat-based help inside the apps people already use
  • Best for: drafting, summarizing, everyday productivity
03

Agent Builder

A lightweight, no-code way to stand up a single-purpose agent.

  • Build directly from Copilot or Teams, no code
  • Scoped to a prompt and a few knowledge sources
  • Best for: one narrow, well-defined job
04

Copilot Studio

The full platform — for multi-step or multi-system workflows, and where the advanced features live.

  • Connectors — link the agent to SharePoint, Dataverse, your ERP, or a ticketing system, so it can act on real data, not just chat about it
  • Agent-to-child-agent — one parent agent that hands off to child agents, each scoped to a single job
  • Advanced: MCP — Model Context Protocol connections to external tools and data sources, for when parent/child agents and connectors still aren't enough

Quick Gut-Check: Which Rung Do You Need?

The pattern I teach: start with one parent agent that owns the front door — it understands the request and routes it. Then add child agents one at a time, each scoped to a single job (look something up, draft a document, update a system through a connector). Every agent stays simple to build, test, and hand off — and it's exactly the roadmap Step 2 produces before anything gets built. One of the first child agents worth building is an adoption agent of its own — scoped to "how do I use this" questions and pointing people to training — so the rollout gets its own AI-powered support desk from day one.

Why not just use Microsoft Learn?

Generic "how to use Copilot" content is free, and Microsoft already gives it away. If a training deliverable reads like it could have come straight from vendor documentation, it hasn't earned its budget line.

The value is in the layer vendor docs can't provide: your ticketing system instead of a generic connector name, your internal naming conventions, your security and compliance posture, and your employees' actual starting skill level. I start where the vendor documentation stops.
